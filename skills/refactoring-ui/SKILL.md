# Refactoring UI — 界面视觉改造

面向「会写代码但没学过设计」的场景：把「让界面变好看」拆成一组可判断、可执行、可验证的决定。

核心命题有三条，后面所有流程都由它们推出：

1. **多数「不好看」不是审美问题，而是层级问题**——所有元素都在抢注意力。
2. **一致性来自有限的预设体系，不来自每次手动调值**——错误不是选错了值，而是没有一个受约束的取值集合。
3. **先做减法（删元素、弱化干扰），再做加法（加装饰）**——装饰解决不了结构问题。

## 何时使用

**使用：**

- 「这个页面看起来不像专业做的」「没设计感」「帮我改好看点」
- 界面层级混乱、重点不突出、信息平铺
- 间距/对齐/留白不均，尺寸随手取值
- 字号、字重、行高、行长没有体系
- 配色杂乱、灰阶不够用、彩色背景上文字发闷
- 需要压平/悬浮/分层效果，但只想到加边框和阴影
- 审查现有 UI、建立或统一设计 token、给新功能定视觉方案

**不使用（直接完成用户的原任务）：**

- 只要求实现交互逻辑、接口、状态管理
- 动效、微交互、滚动叙事设计
- 品牌 VI、Logo、营销插画创作
- 完整的无障碍合规审计（可引用本 Skill 的对比度阈值，但不冒充审计结论）
- 用户只要求解释某个 CSS 属性的行为

## 工作流程

### 0. 先确认三个约束（缺了就问，不要猜）

- **能不能改结构**：能否删元素、改布局、换组件，还是只能调样式？
- **有没有设计系统**：项目已有 token/组件库时，**用它，不要另造一套**。
- **真实内容与设备**：真实文案长度、最长列表项、目标屏幕宽度。

材料不足时按最常见情形推进，并在结论中标明假设，不要停下来反复确认。

### 1. 诊断：先定位到层级，而不是先调样式

按下面的顺序看，**前一层没解决就不要进入下一层**（后面的调整会被前面的结构问题白白抵消）：

| 顺序 | 看什么     | 典型症状                               |
| ---- | ---------- | -------------------------------------- |
| 1    | 信息层级   | 所有文字一样大、一样黑；按钮都同样醒目 |
| 2    | 间距与布局 | 元素贴边、分组分不清、内容硬拉满屏     |
| 3    | 排版       | 字号随手取、行长过宽、行高恒定         |
| 4    | 颜色       | 灰阶不够、靠 lighten/darken 凑色阶     |
| 5    | 层次感     | 全靠 1px 边框分区、阴影只有一种        |
| 6    | 打磨       | 空状态是白板、默认控件裸奔、图片糊     |

能渲染就看渲染结果；只能读代码时，明确声明「未做视觉验证」，不要描述自己没看到的画面。

### 2. 修层级：把重要性映射成视觉权重

先给每个元素定「主 / 次 / 三级」，再**分工**给三个通道，不要都堆给字号：

- **尺寸**：只用于真正的结构差异，不要用它承担全部层级。
- **字重**：2 种足够（400/500 与 600/700）；正文不用 <400。
- **颜色**：文字颜色 ≤3 种（主内容深色、次要中灰、三级浅灰）。

层级不够时，先找**该被弱化的元素**（竞争者），而不是给目标元素继续加码：降对比度、去背景色、缩字号。

### 3. 修间距与布局：留白用减法

- 先给**明显过多**的空间，再往下减到满意——加出来的留白通常只是「不至于难看」的下限。
- 尺寸从**预设阶梯**里取，不手动输入任意值。
- 宽度按内容需要给，用 `max-width` 限上界，不用百分比把元素缩水。
- 分组靠间距而不是边框：**组内间距 < 组间间距**。

### 4. 修排版

- 字号取自一条 9–11 档的阶梯，单个界面实际只用其中 4–6 档（px/rem，不用 em 定义阶梯本身）。
- 行长 45–75 字符（约 20–35em）。
- 行高与行长成正比、与字号成反比。
- 混排字号按基线对齐；数字右对齐；两端对齐必须开断词。

### 5. 修颜色

- 换 HSL 思维：改颜色时分别决定色相、饱和度、明度。
- 每色 5–10 阶，预先定义；禁止用 `lighten()`/`darken()`/临时调透明度生成色阶。
- 明度偏离 50% 时提高饱和度；需要改亮度时优先小幅旋转色相（≤20–30°）。
- 正文对比度 ≥4.5:1，大字 ≥3:1；深底浅字不达标时反向对比。

### 6. 修层次感

- 阴影表达 **z 轴高度**，不是装饰；先用 5 档高度体系，再按「元素该浮多高」选档。
- 悬浮/凹陷优先用**光的方向**表达（上亮下影 / 下亮内影），不要靠加粗边框。
- 需要更细的效果时用双层阴影：大而柔的投影 + 小而暗的接触阴影。

### 7. 打磨（结构没问题之后才做）

空状态、图片尺寸、默认控件样式、背景装饰、强调色边框。顺序不能颠倒。

## 硬性阈值

| 维度          | 规则                                                                          |
| ------------- | ----------------------------------------------------------------------------- |
| 间距/尺寸阶梯 | 相邻档位相对差 ≥25%；以 16px 为基准取因数与倍数                               |
| 字号阶梯      | 阶梯 9–11 档可选、单页用 4–6 档；界面字号 12–72px；不出现 13/15/17 这类噪声值 |
| 行宽          | 每行 45–75 个字符，约 20–35em；超过 75 属于高风险                             |
| 行高          | 正文 1.5–2（行越长越大）；大标题 1–1.2                                        |
| 文字颜色      | ≤3 种；彩色背景上不用灰色文字，用同色相手动调色                               |
| 字重          | 2 种；正文不用 <400，弱化用颜色或字号而不是更细的字重                         |
| 色阶          | 每色 5–10 阶，推荐 9 阶（100/300/500/700/900 为骨架）                         |
| 饱和度        | 明度越偏离 50%，饱和度越高，否则浅/深阶发灰                                   |
| 色相旋转      | ≤20–30°，超过就是换了个颜色                                                   |
| 对比度        | 正文 ≥4.5:1，大字号（≥24px 常规或 ≥19px 粗体）≥3:1                            |
| 阴影          | 5 档高度；高度越高，接触阴影（内层）越轻                                      |
| 图片          | 位图不放大；16–24px 图标不放大；全屏截图不缩小注入小容器                      |

## 关键判断规则（最容易做错的地方）

- **标签是最后手段**：格式（邮箱、电话、价格）或上下文能说明身份时不要加标签；必须加时把标签当辅助（更小、更浅、更轻），合并进值里更好（「库存 12」→「仅剩 12 件」）。
- **语义标签 ≠ 视觉层级**：`h1` 语义正确，视觉上可能应该很小；区块标题多半是标签属性，甚至可以视觉隐藏。
- **语义 ≠ 层级**：页面只有一个主操作；次要操作用描边或低对比底色，三级用链接样式。破坏性操作不必是大红实心按钮，除非它确实是当前页面的主操作。
- **不要为对齐牺牲元素**：元素需要固定宽度就给固定宽度；栅格会让侧边栏在中等屏幕比大屏更宽，这是错的。
- **允许非等比缩放**：大按钮的内边距应该更宽松、小按钮更紧；小屏上大标题要比正文缩得更快。
- **图标天然偏重**：实心图标放在文字旁会盖过文字，用降对比度补偿，而不是放大文字。

## 输出格式

改代码时，按「问题 → 原因（对应规则）→ 改法 → 涉及文件」组织，不要只说「调好看了」：

> **层级**：三张卡片的标题、指标、说明同色同重 → 主指标 700 / 深色，标题 500 / 灰色，说明 400 / 浅灰 → `StatCard.tsx`

只做审查时，按影响排序输出，并标注级别：

- **阻断**：结构性问题（层级缺失、分组不可辨、对比度不达标）
- **建议**：体系性问题（尺寸/字号/色阶未收敛）
- **可选**：打磨项（空状态、装饰、默认控件）

每类最多列 5 条可执行项，附上文件位置；没有问题的维度直接说没问题，不要凑数。

## 边界与失败处理

- **不要过度设计**：不引入新依赖、不换框架、不加动画库；只改视觉，不改行为。
- **尊重既有设计系统**：项目已有 token 时，问题应表述为「偏离系统」或「系统缺一档」，而不是推翻重建。
- **品牌个性优先于规则**：字体、圆角、颜色倾向属于产品决策，用户已定的方向不要按「更稳妥」改掉。
- **无法验证就说明**：没有渲染环境时，不要断言「看起来好多了」；说明哪些判断只来自代码，哪些未验证。
- **原书未覆盖的领域**（复杂动效、图表可视化语法、国际化排版）不要硬套本 Skill 的规则。
