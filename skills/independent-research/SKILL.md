# Independent Research — 先理解，再评价

本 Skill 将“独立思考”转化为可执行、可复查的调研流程。目标不是找到最多链接或收集最多人的意见，而是**基于原始证据建立解释，经受反例检验，并给出有条件的结论**。

方法来源：[如何不被自媒体干扰，真正地独立思考](https://mrsibe.top/posts/independent-thinking/)（方法上的改编）。

## 不可违背的原则

1. **先事实，后评价。** 初始阶段优先研究规范、论文、技术报告、官方文档、源码、原始数据及可复现实验，不以 KOL、媒体标题或社区热度作为结论的起点。
2. **一手资料也要怀疑。** 项目作者对性能、优势和适用范围的描述属于待验证的主张；确认其测量条件、版本、基线和利益相关性。
3. **分别标注事实、推断与观点。** 事实有可追溯依据；推断写出推理链；观点必须依赖明确评价标准。假设、传闻与无法核实的内容不得写成事实。
4. **机制优于口号。** 不满足于“能做到什么”，还要解释关键步骤、因果机制、瓶颈和失败路径。
5. **不存在脱离情境的绝对优劣。** 与实际替代方案比较，写明收益、代价、工作负载、规模、环境、团队能力及失效边界。
6. **社区意见用于挑战初判，而非替代初判。** Reddit、GitHub Issues / Discussions、论坛、HN 等用于寻找真实使用经验、反例和遗漏。高票、高赞、不等于正确或总体共识。
7. **不伪造检索和实验。** 不得编造来源、引文、性能数据、测试记录；无法访问网页、源码或工具时说明限制，依据现有材料给出有界分析及验证路径。

## 工作流

### 0. 确定调研边界与深度

从用户请求中提取：

- **研究对象**：具体产品、概念、技术、论文、项目或争议性断言；明确版本、时间范围和术语歧义。
- **研究目的**：建立概念理解、判断某一主张、做方案比较、选型或落地决策。
- **比较基线**：没有新方案时会如何解决？现有方案是什么？必要时引入合理的候选方案，但标记为假设。
- **决策环境**：目标任务、规模、硬件、成本、可靠性、经验和其他已知约束。
- **深度**：快速（核心证据和结论）、标准（四问 + 反例）、深入（源码/论文细读 + 可复现验证计划）。用户没有指定时选择“标准”，不为非关键缺项反复提问。

调研前明确一句中心问题，例如：“在单机小规模推理负载下，技术 A 相比 B 是否值得采用？”这避免把“全面介绍 A”误当成可决策的研究。

### 1. 第一轮：仅依据一手材料建立事实底座

尽量按与主题匹配的顺序查阅原始材料：

| 研究类型 | 优先资料 | 需要防范的误区 |
| --- | --- | --- |
| 论文或模型 | 原论文、附录、代码、评测协议、数据集卡、技术报告 | 把作者宣称的 SOTA 当作通用结论 |
| 开源项目 | README、官方文档、代码、测试、变更日志、设计提案 | README 未更新、实现与文档不一致 |
| 标准或协议 | 规范、RFC、标准草案、参考实现 | 混淆提案、正式标准与实现行为 |
| 产品或服务 | 官方功能说明、定价/限制、API 文档、变更日志、试用结果 | 将营销话术当作功能证明 |
| 社会/市场主张 | 原始统计、官方文件、公开方法学、原始采访记录 | 把二手报道的转述当作原始数据 |

处理每个重要主张时记录：`主张 → 来源 → 证据具体位置 → 版本/日期 → 条件 → 是否已独立核验`。不要简单堆放来源列表。检索结果中的媒体标题或评论不可避免地可能先被看到，但在完成初判前，应隔离其评价，不作为判断依据。

围绕四个问题做研究：

**What — 它究竟是什么？**

- 用准确、不夹带褒贬的语言定义对象，并界定“它不是什么”。
- 分离“目标、实际功能、宣传主张、已有证据”。
- 如果有“更快、最好、颠覆”等比较措辞，追问相对于谁、衡量什么、在什么条件下、证据在哪。

**Why — 它为什么会出现？**

- 交代出现时的技术或业务背景和约束。
- 找到出现之前的主流方案，以及这些方案的具体痛点。
- 解释推动变化的核心矛盾：是哪一项约束、成本或需求让新方案有意义？
- 区分项目作者宣称的动机与可从历史材料核实的背景。

**How — 它通过什么机制实现？**

- 以输入 → 关键处理阶段 → 输出的顺序描述数据流、控制流或论证逻辑。
- 找到使之有效的关键机制，解释**为什么**机制能缓解上一阶段的痛点。
- 对技术问题优先检查源码、论文公式/伪代码、架构图、真实配置、测试；不能读源码时明确解释停留在哪一层。
- 指出前提条件、隐含假设、瓶颈和失败路径；与既有方案说明“哪些机制真正不同”。

**Trade-off — 它得到了什么，又牺牲了什么？**

- 把收益与代价成对呈现：性能 ↔ 成本、易用性 ↔ 灵活性、吞吐 ↔ 延迟、隔离 ↔ 开销等；仅使用与主题相关的维度。
- 用**相同场景、相同指标**对照替代方案，无法公平比较时明确指出。
- 分析适用条件、不适用条件、迁移与维护成本、团队学习成本及潜在锁定风险。
- 给出条件化判断：“当 X、Y 条件成立且能承担 Z 成本时，A 优于 B；否则未必。”

### 2. 固化初步判断（在读社区评论之前）

先写一份供内部校验的简短 `初判快照`：

- **当前判断**：目前证据最支持的结论是什么？
- **事实依据**：哪几条证据直接支持它？
- **主要推断**：哪些环节只是合理推测？
- **最大不确定性**：哪一项缺失信息最可能推翻结论？
- **可证伪预测**：如果结论不成立，应该观察到什么？

**不要跳过这一阶段直接汇总“社区普遍认为”。** 用户不需要看冗长的内部笔记，但最终报告应能说明结论是否在第二轮被修正。

### 3. 第二轮：引入外部评价并主动证伪

现在才系统阅读第三方视角：Reddit 帖子和讨论串、GitHub Issues / Discussions、HN、独立测评、专业博客和有实测数据的用户报告。对社会科学、政策等议题，选择匹配的专业讨论场所，而不机械要求 Reddit。

使用这些材料回答：

1. **有什么被忽略？** 性能退化、兼容性问题、运营成本、边界案例、负面经验。
2. **最强反方是什么？** 主动搜索能推翻初判的证据，不以稻草人反驳。
3. **不同意见为何存在？** 版本、配置、样本、业务规模、利益和评价标准是否不同？
4. **需要修正什么？** 将新证据映射到初判中的具体主张，记录“维持 / 限定 / 修正 / 推翻”。

优先看有**操作场景、版本信息、复现步骤和具体数据**的讨论；关注发表时间和是否已修复。社区帖子是“有人报告了某现象”的证据，不自动是“该现象普遍存在”的证据。若查不到合适的 Reddit 讨论，可以说明未找到高质量样本，绝不捏造“社区共识”。

### 4. 验证关键争议，而不是仅仅增加阅读量

针对足以影响结论的争议，按照可行性选择：

- **可执行**：做最小可复现实验。事先列出假设、环境、版本、样本、指标、对照组和成功/失败判据；保存观察结果，不在测试后改写判据。
- **不可执行**：核查独立复现或设计一个可执行的验证实验，明确标成**建议实验（未执行）**。
- **没有数据**：明确“证据不足，暂不能判定”，并说清楚补充哪项证据最有价值。

对于变化快的领域，核对资料发布日期与软件版本；区分事件发生日与文章发表日。若相互矛盾，先排查时间、定义、实验环境和比较基线，不强行合并成一个肯定判断。

### 5. 输出：用证据建立可被复查的解释

除非用户指定其他结构，按以下顺序组织：

1. **简短结论及其适用前提**：先告诉用户目前可以知道什么、不能知道什么。
2. **What / Why / How / Trade-off**：解释概念、背景、机制及代价；需要对比时使用表格。
3. **社区观点与反证**：呈现高质量的支持与反对证据及其局限，而非虚构多数意见。
4. **独立判断与修正记录**：指出第一轮的初判是否发生变化、具体因何改变。
5. **验证建议 / 下一步**：如何自己实验、复现或继续学习；按价值与成本排序。
6. **关键参考来源**：原始资料优先，每个关键断言靠近其证据给出处；标记日期/版本和仍未核实的部分。

给出**结论的置信程度及原因**（高 / 中 / 低），不要凭来源数量机械计分。阅读 [report-template.md](references/report-template.md) 获取快速、标准、深入三种表达模板；阅读 [source-checks.md](references/source-checks.md) 处理评测、证据冲突或社区争议时的专项检查。

## 按任务调整，而非机械填表

- **快速问答**：四问可压缩为几个段落，但保留来源、比较基线和适用条件。不因模板而冗长。
- **论文调研**：额外聚焦问题定义、研究历史、方法与公式、实验设计、消融、复现局限。
- **开源技术调研**：额外关注源码实现、架构路径、Issues 的真实故障及项目版本。
- **技术选型**：先明确 workload 与成功指标，再对照方案的条件化优劣；必要时给 PoC 设计。
- **争议主张或热点事件**：先把可检验的事实主张拆开，区分“发生了什么”和“应如何评价”。
- **无法联网或用户禁止检索**：仅对提供的资料和可靠已有知识作有界分析，显式声明未验证的环节；不假装看过网站、GitHub 或 Reddit。

## 最终自检（逐项通过再交付）

- [ ] 有没有从原始材料开始，而不是搬运 KOL 或媒体结论？
- [ ] What、Why、How、Trade-off 是否各自回答了实质问题，而非套话？
- [ ] 关键数据有具体来源、版本、比较基线及必要的实验条件吗？
- [ ] 是否把事实、作者主张、推断和个人判断明确区分？
- [ ] 有没有在阅读社区观点**之前**形成可追溯的初判？
- [ ] 是否检索并认真评估至少一种可能推翻初判的反例（有条件可做）？
- [ ] 是否避免用少数评论代表社区整体？
- [ ] 是否明确“适用 / 不适用 / 需要进一步验证”的条件？
- [ ] 是否坦诚说明没看过、没测过、无法确认的部分？
- [ ] 每条建议是否能追溯到证据和用户的实际目标？
